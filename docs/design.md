# redcoast design

The current design, edited in place and kept short: it says what is true now, not how it got here. Why a decision was made lives in the PR that made it. Only a PR whose purpose is to update the design edits this file; other PRs describe their effect on it under "Design impact".

## 1. What this is, and what it is not

redcoast is a self-hosted gateway for coding-agent subscriptions. It supports Claude Code, and ChatGPT subscriptions for Pi and the Codex CLI (the Codex provider). Client machines never log in to a model account and hold no real token: the gateway holds the subscription tokens of one or more accounts and puts one on each request it forwards.

- One Go module, two binaries: `redcoast` on the gateway host (`redcoast claude serve`; the provider is the first word of every command) and `redcoast-client`, the launcher on client machines.
- One process per provider, each with its own listeners, store and inventory, under the same host name; the launcher fills in the URLs. The bullets below describe the Claude process; the Codex process has the same parts, with the differences given in section 2.
- Two entrypoints shared by all accounts: a reverse proxy that `claude` reaches as `ANTHROPIC_BASE_URL` (inference), and a CONNECT-only forward proxy that it reaches as `HTTPS_PROXY` (everything else the CLI fetches).
- Sessions: before it starts `claude`, the launcher asks for a session credential. The credential authenticates every request for as long as the process lives; the gateway decides which account serves it.
- Quota-aware selection: a session is bound to an account for a lease (1 hour), chosen from the upstream's rate-limit headers against soft and hard thresholds.
- A fixed egress per account: each account has its own upstream HTTP proxy (exit), connection pool and concurrency limit, and all of a session's traffic leaves through its account's exit.
- One SQLite file holds all state (Codex logins are the exception: they stay in files outside it, section 2); a local unix socket is the management interface; upgrades hand the listeners to a new process without dropping streams; optional hourly backups go to any S3-compatible bucket.
- Account facts come from a directory of YAML files (the inventory). Credentials appear there only as references: `op://` (1Password), `env://` or `file://`.

Not in scope:

- A general LLM proxy. Each reverse proxy forwards a few listed request lines to its own provider's upstream only (or a loopback origin in tests).
- Providers other than Claude and Codex.
- Switching accounts in the middle of a request, or replaying one. A switch happens between requests; retries are the CLI's.
- TLS interception. The forward proxy only tunnels.
- Failing over to another exit, or sending account traffic direct. When an exit fails, the request fails.
- High availability: one process and one database file per provider, one host.
- Logging accounts in. Claude tokens are long-lived setup tokens that the gateway never refreshes; an operator rotates them in the secret store and reloads. A Codex account is logged in elsewhere and imported once; from then on the gateway holds its ChatGPT login (`auth.json`) and refreshes it itself.
- Remote Control for sessions that go through the gateway (Claude Code turns it off when `ANTHROPIC_BASE_URL` is not the official host).
- Recording conversations. Capture is off by default, redacted by an allowlist and capped.

## 2. Parts and how they connect

```text
 client machine                                 gateway host
 --------------                                 ------------------------------------------------
 redcoast-client --POST /sessions (machine)---> session (TCP or unix) --+
   | starts claude with BASE_URL, OAUTH_TOKEN=session,                  v
   | HTTPS_PROXY=session@forward                             SQLite store: sessions, bindings,
   v                                                         machines, plans, quota, traffic
 claude --POST /v1/messages (Bearer session)-> reverse --+            ^          |
   +-----CONNECT host:port (Basic session)---> forward --+--bind per request     | VACUUM INTO
                                                |        v                       v
                                   direct hosts |   account transport        backup -> S3
                                                v   (token, pool, exit)
                                          public target  --> account exit --> API, targets
 operator --- admin unix socket: reload, handoff, status, sessions, pause, resume, refresh, machines
 monitor  --- /health          browser --- /dashboard.json and the dashboard page (read-only)
 inventory dir (YAML, direct-hosts.yaml) + op:// | env:// | file:// --> account set (on reload)

 the Codex process, the same parts again on their own ports, store and inventory:
 redcoast-client pi | codex --POST /sessions--> redcoast codex serve
 pi | codex --POST /backend-api/codex/responses (Bearer session JWT)--> reverse --> account exit
   +-------CONNECT host:port (Basic session)----------------------------> forward     |
 workstation --ssh, auth.json on stdin--> admin: import    refresher                  v
                         per account: auth.json (0600) + lock file    auth.openai.com, chatgpt.com
```

`redcoast claude serve --config <file>` reads one YAML file, resolves the inventory's references (all or nothing), opens and checks the store, checks every account's egress, opens or inherits its listeners and tells systemd it is ready. A client machine holds a machine credential whose SHA-256 an operator registered with `machine add`; `redcoast-client claude …` presents it to the session interface over TCP (or nothing, over the local unix socket), gets a session credential bound to its source address, and starts `claude` with the base URL, the session credential as its OAuth token and the forward proxy, all other proxy settings dropped. On each request the gateway checks the credential outside any transaction, then in one write transaction binds the session to an account (keeping, renewing or replacing the lease) and forwards through that account's transport, writing one traffic row; on the way, the account's optional inventory fields `device_id` (64 lower-case hex digits) and `account_uuid` replace the client's in the request body's `metadata.user_id` (invariant 12). The forward proxy refuses the hosts of the deny list (`internal/denylist`) on both routes before it authenticates anything (invariant 10). The session ends when `claude` exits (the launcher deletes it), when its machine is revoked, or after 7 days without a request. An account's quota reading is refreshed on demand (`redcoast claude refresh <alias>` or `--all`, which goes through the accounts one after another): the gateway sends one minimal request with the account's token through the account's own exit, stores the readings in `quota_latest` with source `refresh`, and, after a 2xx answer whose readings are under the hard threshold, ends the account's `upstream_429` pause. An account that is paused for another reason gets no request. `redcoast claude plan --admin-socket` triggers one refresh for each account whose quota unit it raised; nothing polls. An egress check (an IP echo through each exit) runs at start, every 15 minutes and on reload, and pauses an account whose exit IP changed. `reload` re-reads the inventory and swaps the account set after migrating affected sessions in one transaction; `handoff` starts the new binary with the listeners inherited and drains the old process for up to 30 minutes. The Codex process is `redcoast codex serve`, with the sessions, machines, source binding, selection, exits, forward proxy and operations described above, and these differences. It reads a configuration file of its own, with the same keys and other default ports plus a `codex:` section (`accounts_dir`, which may not be the store's directory or inside its backup directory or `dashboard_dir`, and `session_key`, a credential reference); a Claude configuration with that section is refused, and a Codex one refuses `capture_dir`. `redcoast-client pi` and `redcoast-client codex` start Pi or the Codex CLI with a configuration directory of their own that holds no login (`PI_CODING_AGENT_DIR`, `CODEX_HOME`). The session credential is a JWT the gateway signs with `session_key` (HS256), with a made-up `chatgpt_account_id` claim and no expiry, wrapping a random credential of which the store keeps only the SHA-256, so a session's life is set by the store as for Claude; Pi reads it through `apiKey` in `models.json`, which names the environment variable holding it (its built-in `openai-codex` provider), Codex through `env_key` (a custom provider). The launcher turns the clients' own side traffic off: Pi with `PI_OFFLINE=1`, Codex with `-c` options on every start (`feedback.enabled=false` among them) and `--no-daemon`. Both clients send inference to `POST /backend-api/codex/responses`, over SSE only. The reverse proxy puts the account's `Authorization` and `chatgpt-account-id` in place of the client's, rewrites the installation ID (invariant 37) and forwards the rest as it came; it reads quota from the `x-codex-primary-*` and `x-codex-secondary-*` response headers, without relying on `Content-Type`, which the upstream does not send, and closes the upstream connection when the client goes away. A window of 300 minutes is stored as `5h` and one of 10080 minutes as `7d`, so the soft and hard thresholds and selection apply to them as to Claude's; a window of any other length is not read. Each account file of the Codex inventory must have a top-level `installation_id`, a lowercase UUID v4, and an `email`; a file without either is refused when the inventory loads. A login is imported once: an operator logs in on a workstation with a dedicated browser profile and a temporary `CODEX_HOME` and pipes its `auth.json` over ssh into `redcoast codex import <alias>`, which hands it from stdin to the admin socket; the gateway checks its identity (invariant 40), refreshes it at once and keeps it as `<accounts_dir>/<alias>/auth.json`; the workstation deletes the temporary directory and never runs `codex logout`, which would revoke the imported login. From then on the gateway renews the account's tokens itself, through the account's exit, as the Codex CLI does: a sweep every minute renews a login whose access token expires within five minutes, or, when its expiry cannot be read, one last renewed more than eight days ago. A process that starts queues a renewal for each account left paused for `upstream_401` (invariant 39). A renewal that fails other than refused is retried after a minute, then twice as long each time, up to an hour. A renewed login that cannot be written is served from memory, `/health` names the account until the write succeeds, and each later renewal of the account only retries the write; the login is lost, and needs a new import, if the process stops first (invariants 31, 39). An account without a login yet loads, its requests are refused before anything goes upstream, and the first sweep pauses it for `needs_reimport`. Packages: [`cmd/redcoast`](../cmd/redcoast/) (configuration, commands, listeners, handoff), [`cmd/redcoast-client`](../cmd/redcoast-client/), [`claude`](../claude/) (proxies, accounts, egress, reload, capture; these parts take a provider hook, `Provider` in [`claude/provider.go`](../claude/provider.go), for what differs by provider, such as the request allowlist, the credential swap, the 401 check and the quota headers, with Claude as one provider), [`codex`](../codex/) (the session JWT, the allowlist, the rewrites, the 426 and the quota headers of Codex; the logins, their import and renewal), [`session`](../session/) (the store, selection, machines, the session interface), [`credential`](../credential/), [`backup`](../backup/).

Each one links to the test that guards it, or is marked untested. Go tests are named after the file and run in the `go` job, which `check` needs; `e2e/xmachine.py` is the Docker rehearsal (fake upstream, fake exit, fake `claude`), which runs in the `e2e` job when the Go code, `e2e/` or `experiments/` changed, and which `check` does not need.

In a forwarded request that carries an installation ID (the Codex CLI's do, Pi's do not), the installation ID in the `x-codex-turn-metadata` header and in the two places of the body's `client_metadata` is rewritten, at the same length, to the serving account's `installation_id` from the inventory; a request whose installation ID cannot be found (unreadable turn metadata, a body that is not JSON, or a compressed body other than Pi's) is refused before anything goes upstream. 39. At the Codex process an upstream 401 to the token an account serves counts as that token refused (one to a token since renewed pauses nothing), and the pause it causes differs from Claude's (invariants 21 and 22, which hold for the Claude process): the account is paused (`upstream_401`) with no fixed length, the request is not replayed, and one token refresh is queued unless one is already queued; a refresh queued for a 401 that came before a refresh of the account settled takes that refresh's outcome. That refresh, not the quota refresh of invariant 22, is what lifts the pause, once it succeeds and passes the identity check of invariant 40; when the refresh is refused (the token endpoint answers 401, 400 `invalid_grant` or a `refresh_token_expired`, `refresh_token_reused` or `refresh_token_invalidated` code, the login fails invariant 40, or the account has no login), the account is paused for `needs_reimport` until a new import; any other failure keeps the pause and the refresh is retried. [`codex/renew_test.go`](../codex/renew_test.go): `TestUnauthorizedRenewal`, `TestRenewalsAfterRestart`, `TestRenewFailures`, `TestRenewSettled`, `TestDashboardShowsCodexState`; [`claude/renew_test.go`](../claude/renew_test.go): `TestRenewalQueue`; [`session/select_test.go`](../session/select_test.go): `TestEndPause`; [`codex/codex_test.go`](../codex/codex_test.go): `TestUpstreamUnauthorizedPauses`.
40. A Codex login, imported or refreshed, is kept only when the `email` claim of its `id_token` equals the inventory's `email` (ignoring case), its `tokens.account_id` equals the `chatgpt_account_id` in the `id_token`'s `https://api.openai.com/auth` claim, and, when the account already has a login, that account ID is the stored one's; replacing the account means deleting its directory first. The claims are read without verifying the `id_token`'s signature, so the check rests on imports coming only through the admin socket. ## 5. Known issues and next steps

- On the account route, host names are resolved by the exit, so the gateway cannot stop a name that resolves to a private address on the exit's side.
- The gateway trusts the TCP peer address. A proxy or TLS terminator in front of it breaks source binding and the per-source caps.
- A public listener without TLS only logs a warning; it should become fatal. The client trusts only the system CAs.
- `/health` and the dashboard have no authentication. The `Host` and `Origin` checks stop a web page from reading them through DNS rebinding, but anyone who can reach the listener reads both; the dashboard shows each account's email and expected exit IP, so access rests on network access control.
- An upstream 401 whose error body is neither plain nor gzip is not recognized as a refused token, so the account is not paused.
- A launcher killed with SIGKILL leaves its session live, holding a machine slot, until the 7-day idle expiry.
- Backups lose up to an hour; sessions issued after the restored snapshot are unknown and their clients must relaunch. Backups pause for up to 30 minutes after a handoff.
- During a handoff's drain the account and tunnel limits apply per process, so they double; reloads are not coordinated across the two processes.
- Schema migrations are one-way; a rollback across one needs a decision by the operator.
- Plans have no read command.
- The egress check calls one fixed IP echo service and expects a top-level `ip` field; it should be configurable.
- IPv6 CONNECT targets are refused by the syntax check.
- The hi rehearsal's `cancel` case sometimes fails its hygiene check because the gateway container is killed at shutdown; CI leaves it out until the cause is known.
- None of the three clients (Claude Code, Pi, the Codex CLI) has its session IDs or the client machine's content (working directory, user name, `AGENTS.md`, git repositories, OS version and the like) rewritten. A session moved to another account shows the same session ID under both, and an account shared by several machines shows that many environments.
- Two accounts of the same provider must not share an exit, since that provider's upstream would see them as one origin; an account of one provider may share an exit with an account of another. Nothing checks either inventory for a repeated exit yet.
- A Codex login that needs a new import, or a renewed one that could not be written, is only flagged on `/health`, the dashboard and the status command; nobody is notified.
- While a renewed Codex login is not yet written, a 401 to its token only retries the write; the account takes one more 401 before it refreshes again.
- An account paused with no end shows an end time in the year 9999 on the dashboard (its format there is unchecked).
- On macOS, configuration that MDM delivers for `com.openai.codex` outranks the Codex CLI's `-c`, and the launcher does not check it.
- Supporting WebSocket for Codex (invariant 35 refuses it) would need each client WebSocket pinned to one upstream WebSocket of one account until it closes; quota then arrives in a `codex.rate_limits` event in the stream, not in headers.
- It is unknown whether a Codex request cancelled by the client is still metered.
- Open questions for the Codex provider: whether Codex's ID headers are held to known shapes as invariant 12 does for Claude Code; whether a binding may change between the requests of one Codex turn (`x-codex-turn-state`).
