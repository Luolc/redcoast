# redcoast design

The current design, edited in place and kept short: it says what is true now, not how it got here. Why a decision was made lives in the PR that made it. Only a PR whose purpose is to update the design edits this file; other PRs describe their effect on it under "Design impact".

## 1. What this is, and what it is not

redcoast is a self-hosted gateway for coding-agent subscriptions. It supports Claude Code, and ChatGPT subscriptions for Pi and the Codex CLI (the Codex provider). Client machines never log in to a model account and hold no real token: the gateway holds the subscription tokens of one or more accounts and puts one on each request it forwards.

- One Go module, two binaries: `redcoast` on the gateway host (`redcoast claude serve`; the provider is the first word of every command) and `redcoast-client`, the launcher on client machines.
- One process per provider, each with its own listeners, store and inventory, under the same host name; the launcher fills in the URLs. The bullets below describe the Claude process; the Codex process has the same parts, with the differences given in section 2.
- Two entrypoints shared by all accounts: a reverse proxy that `claude` reaches as `ANTHROPIC_BASE_URL` (inference), and a CONNECT-only forward proxy that it reaches as `HTTPS_PROXY` (everything else the CLI fetches).
- Sessions: before it starts `claude`, the launcher asks for a session credential. The credential authenticates every request for as long as the process lives; the gateway decides which account serves it.
- Quota-aware selection: a session is bound to an account for a lease (1 hour), chosen from the upstream's rate-limit headers against soft and hard thresholds.
- A fixed egress per account: each account has its own exit, connection pool and concurrency limit, and all of a session's traffic leaves through its account's exit. An exit is an upstream HTTP proxy, or, for an account the inventory declares direct, the gateway host's own address (invariant 41).
- One SQLite file holds all state (Codex logins are the exception: they stay in files outside it, section 2); a local unix socket is the management interface; upgrades hand the listeners to a new process without dropping streams; optional hourly backups go to any S3-compatible bucket.
- Account facts come from a directory of YAML files (the inventory). Credentials appear there only as references: `op://` (1Password), `env://` or `file://`. The Claude process keeps its accounts in its SQLite file and reads the directory only once, as the source of a first import (section 2, account management); the Codex process keeps reading its directory.

Not in scope:

- A general LLM proxy. Each reverse proxy forwards a few listed request lines to its own provider's upstream only (or a loopback origin in tests).
- Providers other than Claude and Codex.
- Switching accounts in the middle of a request, or replaying one. A switch happens between requests; retries are the CLI's.
- TLS interception. The forward proxy only tunnels.
- Failing over to another exit. When an account's exit fails, the request fails; an account with a proxy never sends its traffic direct instead, and a direct account (invariant 41) never through a proxy. Only after a run of such failures is the account paused, so that its sessions move to other accounts on their next requests (invariant 44).
- High availability: one process and one database file per provider, one host.
- Logging accounts in. Claude tokens are long-lived setup tokens that the gateway never refreshes; an operator rotates them in the secret store, runs `verify` for the account and then `reload`, which reads nothing (invariant 50). A Codex account is logged in elsewhere and imported once; from then on the gateway holds its ChatGPT login (`auth.json`) and refreshes it itself. For a Claude account the gateway still logs in nowhere itself, but when an operator asks for it through the page's route it takes a setup token from a login machine and writes it to the secret store (section 2, setup); it renews no token by itself.
- Remote Control for sessions that go through the gateway (Claude Code turns it off when `ANTHROPIC_BASE_URL` is not the official host).
- Recording conversations. Capture is off by default, redacted by an allowlist and capped.

## 2. Parts and how they connect

```text
 client machine                                 gateway host
 --------------                                 ------------------------------------------------
 redcoast-client --POST /sessions (machine)---> session (TCP or unix) --+
   | starts claude with BASE_URL, OAUTH_TOKEN=session,                  v
   | HTTPS_PROXY=session@forward                             SQLite store: sessions, bindings,
   v                                                         machines, plans, quota, traffic
 claude --POST /v1/messages (Bearer session)-> reverse --+            ^          |
   +-----CONNECT host:port (Basic session)---> forward --+--bind per request     | VACUUM INTO
                                                |        v                       v
                                   direct hosts |   account transport        backup -> S3
                                                v   (token, pool, exit)
                                          public target  --> account exit --> API, targets
 operator --- admin unix socket: reload, handoff, status, sessions, pause, resume, refresh, machines
 monitor  --- /health          browser --- /dashboard.json, the dashboard page, POST /quota/refresh
 inventory dir (YAML, direct-hosts.yaml) + op:// | env:// | file:// --> account set (on reload)

 the Codex process, the same parts again on their own ports, store and inventory:
 redcoast-client pi | codex --POST /sessions--> redcoast codex serve
 pi | codex --POST /backend-api/codex/responses (Bearer session JWT)--> reverse --> account exit
   +-------CONNECT host:port (Basic session)----------------------------> forward     |
 workstation --ssh, auth.json on stdin--> admin: import    refresher                  v
                         per account: auth.json (0600) + lock file    auth.openai.com, chatgpt.com
```

`redcoast claude serve --config <file>` reads one YAML file, resolves the inventory's references, each once (all or nothing; when 1Password still refuses a read for being asked too often after the retries, the process exits with status 75, and every other startup failure exits with 1), opens and checks the store, checks every account's egress, opens or inherits its listeners and tells systemd it is ready. A client machine holds a machine credential whose SHA-256 an operator registered with `machine add`; `redcoast-client claude …` presents it to the session interface over TCP (or nothing, over the local unix socket), gets a session credential bound to its source address, and starts `claude` with the base URL, the session credential as its OAuth token and the forward proxy, all other proxy settings dropped. The session request carries launch metadata: the launcher's PID, the working directory (left out when it would take the metadata past the store's 4096-byte limit), herdr's pane and workspace IDs when set, the client (`claude-code`, `pi` or `codex-cli`) and its version, which the launcher reads by running the client once with `--version`, in `/`, with only `PATH` and `HOME` and every proxy variable pointing at a closed port, for at most 3 seconds; a run that fails, prints no version or is late leaves the version out and does not stop the launch. Of the launch metadata the dashboard shows only the client, when it is one of the three, and a version of the form `<n>.<n>.<n>` with an optional short suffix; the working directory and the other fields never reach it. On each request the gateway checks the credential outside any transaction, then in one write transaction binds the session to an account (keeping, renewing or replacing the lease) and forwards through that account's transport, writing one traffic row; an account whose inventory `proxy` is `direct: true` dials from the gateway itself (invariant 41); on the way, the account's optional inventory fields `device_id` (64 lower-case hex digits) and `account_uuid` replace the client's in the request body's `metadata.user_id` (invariant 12). Of a 200 response with a JSON or event-stream body (one without a `Content-Type` is read as a stream), plain or gzip, the reverse proxy reads the model name and the token counts as it forwards the bytes (invariant 42), and the traffic row keeps them: for Claude the input, output, cache-read and cache-creation tokens; for Codex the input and output tokens, the cached ones counted in the input. When the reverse proxy answers 502 in the upstream's place, the row's `failure` names why with one of the fixed names of `failureOf` in [`claude/proxy.go`](../claude/proxy.go), and one log line gives the account's alias, its exit (the proxy URL without credentials, or `direct`), that name and the milliseconds since the request was forwarded, never the error's text, the URL, a header or a credential. Such a row's result is `upstream_failed`, unless a limit ended the request: its `failure` is then `limit` and its result `idle_timeout` or `max_duration`. Every other row leaves `failure` empty. The forward proxy refuses the hosts of the deny list (`internal/denylist`) on both routes before it authenticates anything (invariant 10). The session ends when `claude` exits (the launcher deletes it), when its machine is revoked, or after 7 days without a request. An account's quota reading is refreshed on demand (`redcoast claude refresh <alias>` or `--all`, which goes through the accounts one after another): the gateway sends one minimal request with the account's token through the account's own exit, stores the readings in `quota_latest` with source `refresh`, and, after a 2xx answer whose readings are under the hard threshold, ends the account's `upstream_429` pause. An account that is paused for another reason gets no request. `redcoast claude plan --admin-socket` triggers one refresh for each account whose quota unit it raised. The Claude dashboard also starts a refresh of every account (invariant 43): `POST /quota/refresh` answers at once and runs, in the background, a round that goes through the accounts as `--all` does, at most one such round at a time and none within 5 minutes after the last one ended. Every 5 minutes the Claude process also refreshes, one after another, each account with a reading at or over the soft threshold, or `rejected`, whose reset has passed: before the reset, selection prefers other accounts to such an account, or never chooses it, so no response might read that window again for long after the reset, while status shows the old reading and the dashboard none. A window that the upstream's latest answer since its reset did not carry, such as a `5h` window an account no longer has, is left out (invariant 22): it keeps its last reading, which selection and the dashboard count as unread, and causes no further refresh. A `--all` refresh, a dashboard round and a periodic recheck never run at the same time: each waits for the one in progress (invariant 43). The Codex process has no quota refresh, so its readings are read only from responses, and its dashboard offers none: its `POST /quota/refresh` answers 501. Each reading that goes into `quota_latest`, from a response or a refresh, also goes into `quota_history` when that window's last reading there is at least 5 minutes old and either differs from it or is at least an hour old; `quota_history` is pruned with the traffic rows, after `retention.traffic_days`, and `/dashboard.json` gives each account's last 5 hours of `5h` readings and last 7 days of `7d` readings. An egress check runs at start, every 15 minutes and on reload: through each exit it reads the exit IP from an IP echo and pauses an account whose exit IP changed, then asks the exit to CONNECT to the host of the process's upstream and sets aside an account whose exit refuses (invariant 23); a direct account's check differs as invariant 41 says. `reload` re-reads the accounts, reads from 1Password only the references that no earlier load read (invariant 50), and swaps the account set after migrating affected sessions in one transaction; `handoff` starts the new binary with the listeners inherited and drains the old process for up to 30 minutes. Each process serves its own dashboard, `/dashboard.json` and the page in `dashboard_dir`, which reads only its own `/dashboard.json` and posts only to its own `/quota/refresh`. `gateway.quota_refresh` gives the state of the dashboard's refresh, null at a process that cannot refresh (Codex), where the page offers no button, and otherwise whether a dashboard round is pending or running, when the last one started and ended, and the time until which a new one is refused; the page's button next to the accounts' quota is disabled while a round is pending or running and until that time, and the page reloads `/dashboard.json` after a click. `gateway.provider` in it names the process's provider, and `gateway.dashboards` lists the other provider's dashboard from the optional key `dashboard_links`: an entry names the other provider, once, with an `http` or `https` URL that has a host and no user name or password, or with `:<port>`, which the gateway resolves to the request's own scheme and `Host` name at that port. The page switches provider by navigating to that dashboard, which checks the `Host` itself; it reads nothing across origins (invariant 28). The Codex process is `redcoast codex serve`, with the sessions, machines, source binding, selection, exits, forward proxy and operations described above, and these differences. It reads a configuration file of its own, with the same keys and other default ports plus a `codex:` section (`accounts_dir`, which may not be the store's directory or inside its backup directory or `dashboard_dir`, and `session_key`, a credential reference); a Claude configuration with that section is refused, and a Codex one refuses `capture_dir`. `redcoast-client pi` and `redcoast-client codex` start Pi or the Codex CLI with a configuration directory of their own that holds no login (`PI_CODING_AGENT_DIR`, `CODEX_HOME`). The session credential is a JWT the gateway signs with `session_key` (HS256), with a made-up `chatgpt_account_id` claim and no expiry, wrapping a random credential of which the store keeps only the SHA-256, so a session's life is set by the store as for Claude; Pi reads it through `apiKey` in `models.json`, which names the environment variable holding it (its built-in `openai-codex` provider), Codex through `env_key` (a custom provider). The launcher turns the clients' own side traffic off: Pi with `PI_OFFLINE=1`, Codex with `-c` options on every start (`feedback.enabled=false` among them) and `--no-daemon`. Both clients send inference to `POST /backend-api/codex/responses`, over SSE only. The reverse proxy puts the account's `Authorization` and `chatgpt-account-id` in place of the client's, rewrites the installation ID (invariant 37) and forwards the rest as it came; it reads quota from the `x-codex-primary-*` and `x-codex-secondary-*` response headers, without relying on `Content-Type`, which the upstream does not send, and closes the upstream connection when the client goes away. A window of 300 minutes is stored as `5h` and one of 10080 minutes as `7d`, so the soft and hard thresholds and selection apply to them as to Claude's; a window of any other length is not read. Each account file of the Codex inventory must have a top-level `installation_id`, a lowercase UUID v4, and an `email`; a file without either is refused when the inventory loads. A login is imported once: an operator logs in on a workstation with a dedicated browser profile and a temporary `CODEX_HOME` and pipes its `auth.json` over ssh into `redcoast codex import <alias>`, which hands it from stdin to the admin socket; the gateway checks its identity (invariant 40), refreshes it at once and keeps it as `<accounts_dir>/<alias>/auth.json`; the workstation deletes the temporary directory and never runs `codex logout`, which would revoke the imported login. From then on the gateway renews the account's tokens itself, through the account's exit, as the Codex CLI does: a sweep every minute renews a login whose access token expires within five minutes, or, when its expiry cannot be read, one last renewed more than eight days ago. A process that starts queues a renewal for each account left paused for `upstream_401` (invariant 39). A renewal that fails other than refused is retried after a minute, then twice as long each time, up to an hour. A renewed login that cannot be written is served from memory, `/health` names the account until the write succeeds, and each later renewal of the account only retries the write; the login is lost, and needs a new import, if the process stops first (invariants 31, 39). An account without a login yet loads, its requests are refused before anything goes upstream, and the first sweep pauses it for `needs_reimport`. Account management replaces the directory as the source of the Claude account set and adds a write path to the Claude dashboard; the Codex process is unchanged. Store: a table `accounts` in the Claude store holds the inventory's fields plus `rev`, timestamps and the verification results below. On the first start with an `inventory` directory configured and no import marker in `settings`, one transaction imports the directory and writes the marker; from then on the table is the source, the directory's account files are ignored from then on, and `reload` re-reads the table in place of the directory with every other step unchanged. The import reads every `<alias>.yaml`, served or not, and is refused, with the alias and the field named and never a value, when the directory does not load as before or when a token or proxy login field of any file is not a credential reference; a row of an account the gateway does not serve (paused, testing, retired or `access: direct`) is stored with only its status, access and references checked. `redcoast claude inventory export --session-db <path> <dir>` writes the table as YAML in the inventory's format, through a read-only connection and only the keys the gateway consumes. `direct-hosts.yaml` stays a file. `/dashboard.json` gives each served account a read-only `config` block (references as strings, never values, with `rev`, times and the last `verify` results) and lists the rows of accounts the gateway does not serve under `unserved_accounts`; `write{enabled, reason, can_create}` says whether the page may write and, when it may not, why, and `proxy_ref_options` lists the proxy logins in use, as reference strings. Fields: `alias` cannot change and nothing is deleted (a `retired` status instead). A new account's `token_ref` is the template `dashboard_write.token_ref_template` (for example `op://<vault>/claude-oauth-token-{alias}/credential`) with `{alias}` replaced, and cannot be edited; the item it names may not exist until the account's first setup creates it, so `verify` reports `token_ok` false until then; without the template no account can be created. A proxy credential reference can only be one already in use by an account in the table. Before a served row is stored its references are read again from the secret store (not stored), so an edit that `reload` would refuse is refused and stored nowhere. A change to the proxy, the exit or a reference voids the verification below and goes through `reload` like any change of an account's exit (invariant 23). Write routes, on the dashboard listener and served by the process's own store (the dashboard's reads keep their read-only connection, invariant 27): `POST /accounts` (creates the account as `testing`), `PATCH /accounts/{alias}` (the changed fields, which include `plan`, written through the plan schedule as `redcoast claude plan schedule` does, and `rev`; 409 on a stale `rev`), `POST /accounts/{alias}/verify` and `POST /accounts/{alias}/activate`; no `DELETE`. A request is JSON of at most 8 KiB with no unknown key, and every field has a fixed format, so no field can carry a credential. Writes need the `Host`, `Origin` and `X-Redcoast-Action` checks of invariant 28, and a TCP peer address inside `dashboard_write.allow_from` (a list of IPs and CIDRs, empty by default, which leaves writes off and answers 403; `/0` refused; `X-Forwarded-For` and `Forwarded` are never read). `account_audit` records the time, source IP, action, alias and the old and new values of each changed field, none of which is a credential; the log line names the fields, never the values. Adding an account takes five steps: `POST /accounts`; the login that puts the token in the secret store (`POST /accounts/{alias}/setup`, below, or by hand, in which case the page's third step shows the token reference and runs `verify`); `verify`, which checks, for an account that is not served, `token_ok` (the reference resolves, which shows the token is in place), `egress_ok` (the egress check of invariant 23 through the account's own exit) and `probe_ok` (one request as in a quota refresh, under the lock of invariant 43), keeping only the booleans and their times; a `PATCH` that sets `account_uuid` and `device_id` (a non-empty device ID is required and must be 64 lower-case hex digits, unique among all accounts); and `activate`, which repeats the three checks, requires a plan, an exit not shared with another served account (at most one direct account), a non-empty `device_id` and a current `rev`, and only then sets `active` and reloads, or answers 409 naming what failed; when a check failed, the results it learned are stored, as an `account-activate` audit row, so that the page shows which one. A write whose reload fails answers 502 and says the account was saved: the row stays and the next reload applies it. `POST /accounts` writes the plan after the account, outside its transaction; when that step fails the account stays as `testing` and the error says so. Setup: `POST /accounts/{alias}/setup`, under the checks of writes above, is sent by the page's button, with `X-Redcoast-Action: account-setup` and a body `{"action": "login_and_token", "rev": ...}`, which logs in and then runs `claude setup-token`; any other action, `token_only` included, is a 400 on the field `action`. Only an account that is `testing` or `active` and whose exit is not direct can be set up, and the route records a task only for it, as `requested`, and answers 202 with the state block at once. It answers 409 `account_status` for an account of any other status, 409 `direct_account` for a direct one (checked after the status), 409 `setup_open` when the account already has a `requested` or `running` task, 409 `rev_stale` when `rev` is stale, and 501 `setup_unavailable` while setup is off (below); a refused request records nothing. A task starts only because someone asked for it: there is no automatic renewal. A login machine, a separate host, reaches the admin socket over an ssh key restricted to the setup commands and, once a minute, asks for a task; it logs in on its own side, runs `claude setup-token`, reports each step to the socket, and hands the token over the same connection. The setup commands are three, each a route of the admin socket. `redcoast claude setup next` (`POST /setup/next`) answers `{"task": null}` or one task, which becomes `running` as it is handed out and carries the account's alias, `action`, `request_id`, `status` (`testing` or `active`), email, `receiver_email` (always present, an empty string when the account has none), `device_id` and proxy block (references and addresses, never the values of the credentials), so the login machine reads no inventory file. `setup report <alias> <request-id> --run-id <id> --state <state> --step <code> [--reason <code>]` (`POST /accounts/{alias}/setup/report`, a JSON body of at most 4 KiB with no unknown key) records one step; `state` is `running`, `needs_human` or `failed`, and `done` is set only by the gateway when a handover succeeds; `profile_exists` (the login tool's browser profile for the account already exists) is a reason of `failed` only. `setup token <alias> <request-id> --run-id <id>` (`POST /accounts/{alias}/setup/token`, the two IDs in the query) reads the token from stdin, at most 4 KiB, and sends it as the raw request body, not inside JSON. The first report of a task sets its `run_id`, which every later report and the handover must carry. A refusal answers with one fixed error code, and the command exits with status 1 as the other admin commands do. The gateway takes a handover only for a task that is `running` and whose `run_id` a report has set, and only with that task's `request_id` and `run_id`; a handover claims the task when its quota request starts (one refused before that, for its body, claims nothing), after which the task takes no other handover and the timeouts below no longer apply to it; the handover as a whole fails with `timeout` 5 minutes after the claim, and a task still claimed when the process starts ends as `failed` with `interrupted`; any other handover is refused and writes nothing. It then sends one quota request with the token through the account's own exit; only when that succeeds does it write the token to the secret store at the account's `token_ref` and reload. A failed quota request or write ends the task as `failed`, drops the token, and leaves `token_ref` and the served set as they were; a failed reload, which comes after the write, ends it as `failed` with the new token in the secret store and the old one still served until the next reload. At most one task runs at a time; the others wait as `requested`, in the order requested. A `running` task fails with `timeout` when 30 minutes pass without a report, or 60 minutes after it was handed out; a `requested` task has no timeout and waits until a login machine takes it (or its account stops being eligible, below). A `requested` task, or a `running` one that no handover has claimed, ends as `failed` with `account_status` or `direct_account` if its account stops being eligible first, so that its handover is refused and writes nothing; a claimed handover is not cut off. A `needs_human`, `done` or `failed` task is closed: it blocks no new task. The write uses the same 1Password credential the gateway reads its references with (invariant 15), and the Claude and Codex processes use one and the same credential. Setup is off unless the configuration turns it on (`setup.enabled`, false by default); while it is off, the setup routes answer 501, `gateway.setup` is null and the page offers no setup, and the Codex process refuses the key. The write sets the one field `token_ref` names, in the vault it names and under the title it gives, for the account that has the task, and in the same write the item's own expiry field `expires` to the UTC date of the write plus one calendar year (a write on 29 February 2028 is dated 1 March 2029); an existing item without an expiry field gets the token only, and no field is added. When the item does not exist, the gateway first creates it, with the token field (the category API Credential, the field concealed) and an expiry field, and then reads the item's fields back: a field besides those two (a second expiry field counts) ends the task as `failed` with `created_item_has_other_fields` and `written: true`, leaves the item as it is and reloads nothing. The expiry field is matched by its title `expires`, ignoring case, never by its ID. It writes, to create or to change, only when `token_ref` is what `dashboard_write.token_ref_template` gives for the alias, and refuses otherwise; it never adds a field to an existing item, and creates, changes and deletes nothing else. It refuses, writing and creating nothing, when the vault is missing or matches more than one, when `token_ref` has a section part or names `expires` itself, when the item has two expiry fields, when the item exists but has no field `token_ref` names or has it more than once, when an archived item has the title or more than one item does, and, whether the item exists or not, when `token_ref` is not what the template gives for the alias or no template is set. A failed or refused create leaves the vault as it was; the gateway never deletes an item to undo a write, so an item it created stays when a later step fails. The account carries a state block `{state, request_id, run_id, step, reason, updated_at, token_set_at, action, identity, token_expiry}`, which `/dashboard.json` also gives; only the gateway writes it: the page's request sets `requested`, the three commands and the timeout move it on, and no browser route changes it, so the page has no button that marks an account as logged in; `state` is `not_started`, `requested`, `running`, `needs_human`, `done` or `failed`. `step` and `reason` are each one of a fixed set of codes, never text from the login machine, so they cannot carry a token. `action` is the task's (`login_and_token`); `identity` is null until the open question in section 5 is settled, and will then be `checked` or `unchecked`. When the login meets a captcha or a page it cannot go on from, the state becomes `needs_human` (only with the reasons `captcha_challenge`, `unknown_page` and `email_rejected`; every other cause is `failed`) and the token is put in the secret store by hand, as before; `verify` then shows it. `token_set_at` is when the gateway wrote the token, null for a token it did not write. The gateway's table holds no due date: `token_expiry` is `{state, expires_at, read_at}`, the `expires` field of the item at the account's `token_ref`, hand-placed items included, which the gateway reads once, at start, over one listing of the vaults and of each vault's items, ending the pass at a rate limit; a handover records the date it wrote (`no_field` when the item has no expiry field) without reading the item back, an account write reads nothing, and a date that could not be read stays so until the next start; `state` is `read`, `no_field` (the item has no expiry field), `unreadable` (the item, the vault or the date cannot be read, an item that does not exist yet included) or `unavailable` (not read yet). A failed read changes only that account's entry and blocks no other data, and no token is read: the read returns the values of expiry fields only. The date is the year a setup token is documented to last; nothing queues a task, and `/health` shows no due line, when it nears. The old token is not revoked. `/dashboard.json` gives, under `gateway.setup` (null at the Codex process), whether setup is enabled, the number of queued tasks and when a login machine last asked for one. `/dashboard.json` also gives each account `burn` and `totals`. `burn` per window (`5h`, `7d`) holds a least-squares rate per hour over the readings since the window's last reset (a fall in utilization counts as a reset), the time it reaches 100%, whether that is before the reset and the span used, or null with the reason when fewer than 3 readings or less than 30 minutes remain; `burn.by_machine` splits the rate by each machine's share of the account's tokens in the same period and is marked as an estimate. `totals` gives requests and the four token counts for 24 hours and 7 days, from `traffic`. The Codex process answers the write routes with 501 and `/dashboard.json` gives `accounts_editable: false`. The page has a Manage view (list, editable detail, the five steps) and shows the per-machine rate there only, labeled as an estimate, and asks the user to confirm before it saves a change to an account's settings and before it activates an account; it has no field that takes a credential. Agent access and the creation record. The admin socket has five commands that add an account the way the page does, so that an agent given an email and a plan can run the whole path, and the Manage page shows what happened. `redcoast claude account create <alias> ...` creates the account as `testing` (the flags give the email, the plan and the proxy; `access` is always `gateway`, and a direct account cannot be created this way); `account show <alias>` is read-only and gives the account's `config` block, whether it is served, its state block, its creation record and up to 100 rows of its audit history; `account verify <alias>` and `account activate <alias> --rev <n>` run the page's `verify` and `activate`; `account set <alias> --rev <n> [--receiver-email …] [--device-id …] [--proxy-provider …] [--proxy-type …]` edits an account's receiver email, device ID, proxy provider and type, at the revision given, with the same checks and validations as the page's edit (409 on a stale revision); at least one field flag is required, a flag given with an empty value clears the field, a flag left out leaves it unchanged, and `--device-id` takes 64 lower-case hex digits and only for a `testing` account; `setup request <alias> --rev <n>` asks for a `login_and_token` task as the page's button does, and answers 200 with the state block. They share the page's functions and mutex, so their checks, audit and reload are the same; they do not use the page's `Host`, `Origin`, `X-Redcoast-Action` and `allow_from` checks, which guard a browser: the boundary of the admin socket is the socket and a switch, `admin_write.enabled`, which is false by default and, while it is false, makes every write command (create, `setup request`, verify, activate) answer 501 `account_write_unavailable` and record nothing (invariant 45). A refusal is `{"error": <code>, "field"?, "check"?}` with a fixed code, never a sentence, and the command prints `<route> refused: <code>` and exits 1, as the setup commands do. `account activate` through the socket activates only an account that is `testing`, with the page's criteria otherwise, and answers 409 `not_ready` with `check: status` for any other status; the page's `activate` is unchanged, so the socket is stricter than the page. Every write command carries `source`, `{kind: "slack", thread: "<CHANNEL/TS>", ts: "<TS>"}`, checked for its format only (400 `source_missing`, `source_invalid`): the gateway checks neither that the channel nor that the message exists. The source goes into the audit row and into the setup task, a write from the page records the source IP as before, and an admin write records `admin-socket` as its source IP; every accepted `setup report` also writes one audit row, action `account-setup-report`, that holds only the codes and time it reported (`state`, `step`, and when set `reason` and `wait_until`) and the task's source when the task is a `slack` one, and a refused report writes none; the source is a record and is never evidence that anyone agreed to the write (invariant 49). Two kinds of setup task keep the login machine and an agent apart. A task has a source, `dashboard` for the page's button and `slack` for `setup request`. `setup next` with no argument hands out only a `dashboard` task, as the login machine's poll does, and skips a `slack` one; `setup next --request-id <id>` hands out only that `slack` task if it is `requested` and is the account's latest, answers `{"task": null}` while another task runs, and refuses with 404 `task_not_found`, 409 `task_not_slack` or `task_not_requested` otherwise. `setup report` and `setup token` must carry `--source-kind`, equal to the task's source, or answer 409 `source_mismatch` and write and claim nothing; the gateway does not know who calls, so the commands of each key are fixed by the wrapper on the gateway host that holds the ssh keys, which gives the login machine's key `dashboard` and the agent's key `slack`, and no other command. `setup report` also takes the step `awaiting_captcha` with `--wait-until <RFC 3339>`, only with the state `running`, later than the report and at most 20 minutes after it, set once per task (400 `wait_until_invalid` otherwise); the state block then has `wait_until`, which the next report of another step clears, and the page says it is waiting for a person to pass the captcha and when it times out (HH:MM UTC). The login tool itself reports `needs_human` with `captcha_challenge` when the time comes; the gateway adds no new timeout, the existing no-report timeout still covers the wait, and it sends no message. The detail page of an account shows a timeline, its "Record" section: the creation record (time, source, who), then each write and each step of every setup task with its time, source and result, where the task stopped and why, and the wait for a captcha. The page reads it from `GET /accounts/{alias}/record` on the dashboard listener, which calls the function `account show` calls, so the two give the same record. The route changes nothing, so it has the guards of `/dashboard.json` (invariant 28) and not the write checks; it answers 501 `account_write_unavailable` unless `dashboard_write.allow_from` is set, and 501 at a gateway with no account writer. The page words a source as a record only, never as an approval. No credential is in the record, the log or an answer. The page's path to add an account needs no agent: it works from the page, the gateway and the login machine alone, including when no account of the gateway can serve. Schema (version 12): a migration that adds columns for the source of an audit row and of a task, for `wait_until` and for the flag that it was set. Direct exits:

41. An account file whose `proxy` has `direct: true`, an `expected_egress_ip` and none of `host`, `port`, `username_ref` and `password_ref` declares a direct exit, the gateway host's own address of the family of `expected_egress_ip`; `direct: true` with any of the four, or a `proxy` without `direct: true` that lacks one, is refused when the inventory loads, naming the field. A served account is direct only so: a missing `proxy` is an error, never a direct exit. At most one served account of an inventory is direct, since two would share one exit (section 5); a second is refused, naming both aliases. A direct account's traffic never goes through a proxy, and every dial of it uses only addresses of the family of `expected_egress_ip` (IPv4 or IPv6), so the gateway's other address is never its origin; a target with no address of that family is a failed dial. The forward proxy's account route of a direct account resolves the client's target at the gateway and dials only its public addresses, with no exception, as invariant 11 dials a direct host, and only at port 443: a CONNECT bound to a direct account to any other port gets 403 and nothing is dialed. The deny list and the non-public literal check of invariant 10 still come before authentication. The egress check of a direct account reads the IP echo from the gateway with no proxy and compares it with `expected_egress_ip`, pausing as invariant 23 does. Unless the IP differs, it then dials the host of the process's `upstream` at its port and closes the connection once it connects, sending nothing; no CONNECT is asked. A dial that connects counts as the exit's 200: it ends nothing, since a direct account is never set aside. A dial that fails (no address of the family, a refused connection, a timeout) counts as a CONNECT that got no answer: it sets nothing aside and marks health degraded until a check connects. Upstream failures:

44. Five `upstream_failed` requests of one account that count against it, within 2 minutes and with no upstream response through the account in between, pause the account for 5 minutes with the reason `upstream_failed`. Any upstream response, a 101 the gateway refuses included, ends the account's run; a failure 2 minutes old or older drops out of it; a completed run starts over. Whether a request counts goes by its `failure` (section 2): `egress_dial`, `egress_connect_<status>`, `egress_unanswered`, `dial` and `tls` happen before the transport has a connection for the request, which reads nothing of it, and count as they are; `reset` and `response_header_timeout` count only when the client's body was read to its end without a read error (it had none, its read returned `io.EOF`, or its declared `Content-Length` was read); every other name never counts, among them those of a client that left or broke its body, a limit, a stop, the guard, an upgrade and `other`. The pause is written to the store like any other, so it never shortens one in effect (invariant 21), the sessions bound to the account rebind on their next request, and it holds across a reload and a handoff; it ends on its own when its time is up, or at `resume`. The runs are held in the process's memory by alias: a reload keeps them, a new process starts with none. `upstream_failed` is not a quota reason, so when every account is out and one of them for this reason the answer is 503 (invariant 19). `/health` names the reason as it is. ## 5. Known issues and next steps

- On the account route of an account with a proxy, host names are resolved by the exit, so the gateway cannot stop a name that resolves to a private address on the exit's side.
- The gateway trusts the TCP peer address. A proxy or TLS terminator in front of it breaks source binding and the per-source caps.
- A public listener without TLS only logs a warning; it should become fatal. The client trusts only the system CAs.
- `/health` and the dashboard have no authentication. The `Host` and `Origin` checks stop a web page from reading them through DNS rebinding, but anyone who can reach the listener reads both; the dashboard shows each account's email and expected exit IP, so access rests on network access control. The checks of `POST /quota/refresh` (invariant 43) stop a page of another origin from sending it, but any program that reaches the listener can set `Origin` and the header and start a round, which sends one request with each account's token through its exit and can end an `upstream_429` pause (invariant 22); only the 5-minute wait bounds how often.
- The wait between dashboard rounds (invariant 43) is held in memory: a restart or a handoff starts without it, so a round can follow the last one within 5 minutes.
- A `--all` refresh waits for a dashboard round or a periodic recheck in progress (invariant 43), but the command's own wait, about ten minutes, is sized for its own round alone: with more than ten accounts that each take the 30-second bound, it can give up before its round ends, which then stops.
- The periodic recheck (invariant 22) cannot tell a window the upstream no longer gives from one whose headers a single answer after its reset lacked or garbled: either way the window is not rechecked, and its reading stays as it was, unread for selection and the dashboard, until an answer carries the window again.
- An upstream 401 whose error body is neither plain nor gzip is not recognized as a refused token, so the account is not paused.
- A response that breaks off after its head was sent (result `incomplete`) gets no `failure` name and no log line, and does not count toward a run of invariant 44, so an account whose upstream connections drop mid-response is never paused for it.
- A timeout awaiting the response head (30 seconds) counts toward a run of invariant 44. A client holding a valid session can send well-formed requests that the upstream cannot answer within 30 seconds and, five of them within 2 minutes, pause the account its session is bound to for 5 minutes; every session bound there then moves to another account on its next request.
- Two failures after a connection that only the error's text tells apart, an HTTP/2 GOAWAY followed by a close and the transport's "server closed idle connection", are named `other` and never count toward a run of invariant 44.
- The dashboard has no label of its own for an `upstream_failed` pause and shows it as a plain "Paused".
- A launcher killed with SIGKILL leaves its session live, holding a machine slot, until the 7-day idle expiry.
- Backups lose up to an hour; sessions issued after the restored snapshot are unknown and their clients must relaunch. Backups pause for up to 30 minutes after a handoff.
- During a handoff's drain the account and tunnel limits apply per process, so they double; reloads are not coordinated across the two processes.
- Schema migrations are one-way; a rollback across one needs a decision by the operator.
- Plans have no read command.
- The egress check calls one fixed IP echo service and expects a top-level `ip` field; it should be configurable.
- IPv6 CONNECT targets are refused by the syntax check.
- The hi rehearsal's `cancel` case sometimes fails its hygiene check because the gateway container is killed at shutdown (exit 137); its `tui` case failed once on `main` the same way. CI leaves `cancel` out until the cause is known.
- None of the three clients (Claude Code, Pi, the Codex CLI) has its session IDs or the client machine's content (working directory, user name, `AGENTS.md`, git repositories, OS version and the like) rewritten. A session moved to another account shows the same session ID under both, and an account shared by several machines shows that many environments.
- Two accounts of the same provider must not share an exit, since that provider's upstream would see them as one origin; an account of one provider may share an exit with an account of another. Nothing checks either inventory for a repeated proxy yet; only a second direct account is refused (invariant 41). `activate` checks it for the Claude accounts (section 2, account management); the first import does not check it, and whether it should is undecided.
- The reach check of a direct account (invariant 41) only dials the upstream's port: an upstream that refuses the gateway's address only once TLS or a request begins (a 403 from the origin, say) passes it.
- A Codex login that needs a new import, or a renewed one that could not be written, is only flagged on `/health`, the dashboard and the status command; nobody is notified.
- While a renewed Codex login is not yet written, a 401 to its token only retries the write; the account takes one more 401 before it refreshes again.
- `/dashboard.json` gives hourly figures for the last 24 hours only (daily counts for 7 days), though the traffic rows an hourly view of 7 days needs are kept for `retention.traffic_days`.
- A request's duration runs until its response finished streaming; nothing records the time to the first byte, so the dashboard cannot show it.
- On macOS, configuration that MDM delivers for `com.openai.codex` outranks the Codex CLI's `-c`, and the launcher does not check it.
- Supporting WebSocket for Codex (invariant 35 refuses it) would need each client WebSocket pinned to one upstream WebSocket of one account until it closes; quota then arrives in a `codex.rate_limits` event in the stream, not in headers.
- It is unknown whether a Codex request cancelled by the client is still metered.
- Open questions for the Codex provider: whether Codex's ID headers are held to known shapes as invariant 12 does for Claude Code; whether a binding may change between the requests of one Codex turn (`x-codex-turn-state`).
- The write path of account management (section 2) is on a dashboard listener that has no authentication: the boundary is network reach plus the source-address list, with no login, so access rests on the network and on the list being short. A change to an account no longer passes a pull request review, so the checks of invariants 45 to 47 are the whole gate. The admin socket is also reached by the login machine over an ssh key restricted to the setup commands; whoever holds that key can take tasks and hand over a token, but the gateway writes a token only after the quota request of invariant 48. An agent reaches it over a second key, restricted to the commands of the agent's path; the gateway does not authenticate who calls the socket, so that the two keys cannot reach each other's tasks rests on the wrapper that fixes each key's commands and `--source-kind` (invariant 49), and the source an agent gives is its own statement, which the gateway records and does not check. The credential the gateway reads its references with also has write access to the secret store, so a flaw in any code that holds it can change or create an item there, not only read it; invariant 48 limits what the gateway writes, not what that credential could. The Codex process holds the same credential and so has the same access, although it refuses the setup routes.
- The audit row of a plan change is written after the plan, in a transaction of its own; when that fails it is logged and the plan change stands, so a landed plan change can lack its audit row.
- Open: how the gateway knows that a token that passes the quota request in setup (section 2) is the account's own, which the quota request alone does not tell. One candidate is to compare an account-identity header of the answer with the one last seen on a 2xx answer to the account's current token, keeping only a hash of it; whether the answer to a setup token's request carries such a header, and whether an account always gets the same value, is not known. Until it is settled, only the login machine's own check of the logged-in account covers this, and `identity` stays null.
- Open: facts about the secret store's SDK that setup (section 2) relies on and that nobody has checked against a real vault: whether a service account's write permission includes creating an item; whether creating an item accepts a field with an ID of its own; the ID, the type and the value format of the API Credential category's expiry field (the gateway matches it by title and writes `YYYY-MM-DD`); whether creating an item of that category adds fields of the category's own, a second expiry field among them (the read-back after a create ends the task if it does, and every later handover to that account is then refused until a person fixes the item); whether an archived item is resolved by an `op://` reference; and what a write does to an item that changed since it was read. The adapter to the SDK has no test against a real vault.
- Open: whether a setup token stops working at the expiry date the gateway writes or later; the year is the documented life of the token, and what happens at its end is not known.
- Open: whether the Codex process gets account management; it would need a restricted way to import `auth.json`, which holds credential values.
